## Зачем

Цель — конвейер без ручной копипасты: **Куралай** ставит карточку → **Земля** (bilem-earth) делает инструмент MCP в расширении `bilem.cfe` на стенде → Куралай проверяет через MCP → слияние в `dev` → следующая карточка. Слава вмешивается только при стопе (andon).

Одна карточка за раз. Ошибка → стоп конвейера, а не обход. Максимум 2 круга ревью.

<Steps>

  <Step title="Земля делает">

  </Step>
  <Step title="Передача Куралай">
    Итог одним комментарием → **переназначить на Куралай** (статус todo). `in_review` API не принимает: у проекта нет review path для агента — не пробовать.
  </Step>
  <Step title="Приёмка">
    Куралай вызывает инструмент через свой MCP bilem (`openclaw mcp reload` или `bilem_help`/`bilem_call`), сверяет с приёмкой. Не так — назад Земле (до 2 кругов).
  </Step>
  <Step title="Слияние и закрытие">
    Принято → Земля сливает ветку в `dev` (merge, без force) → Куралай закрывает, обновляет [Что уже работает](/cfe/tools-live), ставит следующую.
  </Step>

## Мост earth-bridge (Paperclip → стенд)

Исходник: `minidesk/tools/earth-bridge/earth-bridge.mjs` (+ `README.md`, `restart-bridge.ps1`). На стенде — `C:\bilem\earth-bridge\`, задача планировщика `\Bilem\Earth-Bridge`, лог `earth-bridge.log`.

Как работает (версия `366ff05`):

1. Paperclip (HTTP-адаптер bilem-earth) шлёт `POST /wake` с заголовком `x-bridge-secret` на tailnet-адрес стенда, порт 8790.
2. Мост **сразу отвечает 202** и ставит задание в очередь (одно на задачу; лишние пинки `repair/recovery/monitor` и пробуждения от собственных комментариев отбрасывает).
3. По очереди запускает `claude -p --permission-mode bypassPermissions` в рабочей папке репо. Переменные рана: `PAPERCLIP_API_URL/KEY`, `PAPERCLIP_RUN_ID`, `PAPERCLIP_TASK_ID`, `PAPERCLIP_WAKE_REASON`. Коннекторы Paperclip — временный `--mcp-config` с сервером `paperclip`.
4. Claude сам пишет в задачу через API (с `X-Paperclip-Run-Id`).
5. Если ран упал или превысил `RUN_TIMEOUT_MIN` (20) — мост убивает **всё дерево** процессов (`taskkill /T /F`) и сам пишет в задачу комментарий с причиной + статус **blocked**. Повтор — обычным комментарием.

`.env` (в git не кладём): `BRIDGE_HOST`, `BRIDGE_PORT`, `BRIDGE_SECRET`, `PAPERCLIP_API_URL`, `PAPERCLIP_API_KEY`, `WORK_DIR`, `CLAUDE_CMD`, `RUN_TIMEOUT_MIN`, необязательно `EXTRA_PATH`, `START_COMMENT=1`, `CLAUDE_PERMISSION_MODE`.

Перезапуск: `powershell -ExecutionPolicy Bypass -File C:\bilem\earth-bridge\restart-bridge.ps1` — сам повышает права, ждёт конца рана (или `-Force`), снимает задачу, добивает node на порту (`schtasks /End` его не убивает), запускает и проверяет `/health`.

## Среда рана на стенде — что уже наступили

| Грабли | Как решено |

| Под планировщиком урезанный PATH, `git` не находится | Поставлен Git for Windows (`winget install Git.Git`); мост дописывает `C:\Program Files\Git\cmd` и `EXTRA_PATH` |

| Клик мышью в консоль → заголовок «Выбрать…», процесс заморожен | Отключить «Выделение мышью» (QuickEdit) в умолчаниях консоли; в окно моста не кликать |

## 1С: EDT-MCP вместо Конфигуратора

EDT открыт **для агента** и держит блокировку базы — Конфигуратор при открытом EDT не работает («Ошибка блокировки информационной базы для конфигурирования»). Поэтому:

- **Конфигуратор (`1cv8 DESIGNER`) не используем ни для чего** — ни загрузка, ни выгрузка.
- Загрузка в базу — EDT-MCP `update_database` (обычное, инкрементальное). **`fullUpdate` не запускать**: требует монопольный доступ, а базу (файловая, `1Cv8.1CD`) держит IIS-публикация → EDT показывает модальное «Ошибка исключительной блокировки…» и всё виснет.
- Заимствование объектов в расширение — EDT-MCP `adopt_metadata_object`.
- После изменений EDT должен увидеть файлы с диска (`resync_to_disk`/refresh). EDT-проект должен указывать на ту же папку, где работает Земля.
- Проверка — **только через публикацию `/lakomka-api`** (`/hs/bilem/mcp/<token>`). На `/lakomka` HTTP-сервиса bilem нет — 404 там нормален (13.10 Земля приняла это за «расширение не подключено»).
- Если EDT-MCP не отвечает или требует монопольный режим — **blocked с текстом ошибки**, без обходов.

Настройки EDT-MCP (DitriXNew, 2.20.1; Window → Preferences → Сервер MCP): порт 8765, только loopback, «Автоматически запускать вместе с EDT» — вкл, деструктивные операции — «Разрешать всё без запроса» (решение Славы: учебная база, есть бэкапы и git; **для баз клиентов — только «спрашивать»**). Ярлык EDT — в `shell:startup` пользователя `bakanov`; RDP закрывать «Отключиться», не «Выйти».

## Paperclip: как устроено и где ломается

**Запись в задачу.** Все мутации — с `X-Paperclip-Run-Id` (без него 403 `cross_issue_influence_run_context_required`). Checkout задачи — в том же ране (иначе 409 run ownership conflict). Писать можно и после окончания рана: сервер проверяет принадлежность рана агенту и задаче, а не активность.

**Recovery — главная грабля (разбор дежурного 13.10).**

- Любой ран со статусом `failed`, `timed_out`, `interrupted` или `cancelled` у адаптеров `http`/`openclaw_gateway` создаёт запись сверки, и задача получает `automaticRecovery.replay = blocked` — плашка **«Automatic recovery of this task stopped»**.
- Блок — **на задачу, а не на агента**: все пробуждения (комментарий, назначение, monitor) уходят в очередь «Waiting for execution recovery. Your message is saved». Comment/Interrupt не проходят (работают только для «разговорных» адаптеров), Retry — только для failed/timed_out.
- **Переназначение во время рана** отменяет его (`issue_reassigned`) — тоже блок. Правило: **не переназначать, пока агент работает**.
- **HTTP-адаптер ждёт ответ максимум 300 с** (лимит fetch при адресе-IP; при имени хоста — 30 с), независимо от `timeoutMs`. Любой не-2xx или обрыв = `adapter_failed` = блок. Поэтому мост отвечает 202 сразу, а ошибки пишет в задачу сам. Рекомендуемый `timeoutMs` агента — 30000.
- **Снять блок может только борд**: «сверка исполнения» на плашке или `POST /api/issues/:id/recovery-actions/resolve` с `outcome: restored` и `executionReconciliation` (runId, providerStopped, actionOutcome, outcomeEvidence ≥ 20 символов). Быстрый обход — отменить задачу и создать новую (работа в ветке не теряется).
- Watchdog и Monitor — поля задачи, не проекта; от блока не спасают. Описание проекта в контекст пробуждения не попадает — агент читает `GET /api/projects/:id` сам.
- Черновики upstream-issue (блок при `outcome=cancelled` и область фильтра; `timeoutMs` HTTP-адаптера) — у дежурного, не опубликованы.

**Прочее.** Новые агенты — через апрув борда. Коннекторы Paperclip (Fathom, Bilem, Mintlify) отдаются рану через `PAPERCLIP_RUNTIME_TOOLS_*`; `openclaw_gateway` их в текст пробуждения не кладёт (кандидат в PR), поэтому у Куралай Bilem подключён напрямую (`openclaw mcp add bilem …`). `tools/list` клиент кэширует до переподключения — для новых команд есть `bilem_help`/`bilem_call`.

## Если конвейер встал

1. Лог моста: последние строки `принят` / `готово` / `таймаут`. Нет `принят` после назначения → смотри плашку recovery в задаче.
2. Плашка recovery → сверка борда или новая карточка с той же веткой.
3. На стенде: нет ли модального окна (EDT, 1С), консоли в режиме «Выбрать», зависшего `1cv8`.
4. `whoami` через `/lakomka-api` — живо ли расширение и какая версия.
5. Земля упёрлась в лимит подписки Claude → ждать сброса, задача остаётся как есть.
