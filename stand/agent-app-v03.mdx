## Часть B — черновики и подтверждение

### Принцип

Инструменты записи **ничего не пишут в 1С сами**: они создают **черновик в агенте** и возвращают «ждёт подтверждения» + превью. В 1С записывает только кнопка **«Подтвердить» в агенте** (мимо модели). Только объекты белого списка и только там, где запись включена на «Доступе». Документы — непроведённые.

### Окно подтверждения

- При новом черновике — окно агента «Подтвердите действие» поверх остальных (не модальное) + уведомление в трее. В окне: база, что создаём, все поля (для счёта — превью PDF), предупреждения («такой БИН уже есть», «нет договора»), кнопки **«Подтвердить» / «Отклонить»**.
- Несколько черновиков — очередь списком. Черновик живёт 24 ч, потом исчезает.
- ИИ узнаёт итог инструментом `draft_status(id)` (подтверждён → ссылка/номер в 1С; отклонён; ждёт).
- История — в «Журнале» (что, кто подтвердил, когда), без содержимого.
- Облако (серый блок): подтверждение с телефона, кто имеет право подтверждать.

### Инструменты MCP

| Инструмент | Что делает |
| --- | --- |
| `find_counterparty` | + поиск по БИН/ИИН с **проверкой контрольной суммы** (алгоритм РК); неверный — сразу ошибка «БИН с ошибкой» |
| `draft_counterparty` | черновик контрагента (наименование, БИН/ИИН, адрес, телефон, e-mail) + по желанию банковский счёт (ИИК, БИК → банк из справочника) и договор. **Если БИН уже есть — черновик не создаётся**, возвращается найденный |
| `draft_invoice` | черновик счёта: контрагент (ссылка или id черновика контрагента), строки (содержание, кол-во, цена; номенклатура — только существующая), договор, **банковский счёт организации по умолчанию — основной**, НДС — по настройкам организации и номенклатуры; «Содержание» строки заполняется явно |
| `copy_invoice` | «выставь как в прошлом месяце»: черновик по образцу существующего счёта со всеми реквизитами, меняются дата, период в содержании, количества (идея из [разбора](/product/konkurenty)) |
| `draft_status` | состояние черновика |

Счета учёта (если нужны документу) — из регистра «Счета учёта номенклатуры», не выдумывать. Доверенность и акт сверки — следующим шагом (после приёмки счёта).

### Приёмка B (v19/v20)

- Текст реквизитов нового ТОО → `draft_counterparty` → окно подтверждения → «Подтвердить» → контрагент в 1С; повтор с тем же БИН — «уже есть», дубля нет.
- `draft_invoice` → превью PDF в окне → «Подтвердить» → счёт в 1С непроведённым, печать на нём = превью; в 1С счёт открывается и печатается их формой без пустых полей.
- «Отклонить» — в 1С ничего; запись выключена на «Доступе» — инструмент сразу отказывает.
- ИИ не может подтвердить сам (нет такого инструмента — тест).

## Часть C — вкладка «Почта» ([0014](/decisions/0014-pochta-predohraniteli))

### Настройки (на каждую базу)

- SMTP: сервер, порт, SSL/TLS, логин, **пароль приложения** (DPAPI), имя отправителя; подсказки для Gmail / Mail.ru / Yandex / Outlook; «Проверить» — письмо себе.
- **Скрытая копия себе** — вкл. (адрес по умолчанию — ящик отправителя).
- **Лимиты** — 10 в час, 50 в день (настраиваемо).
- **Адреса для доверенностей** — список своих адресов (главбух, директор); доверенность уходит только туда.
- Шаблон темы и текста письма (РУ/КЗ), подпись отправителя.
- **«Почта выключена»** — рубильник (и в меню трея).
- Облако (серый блок): подтверждение с телефона, права по людям, цепочки одобрений.

### Инструмент `send_document`

- `base`, документ (счёт по номеру / из черновика), необязательная приписка (до 300 символов). **Адресата модель не передаёт**: для счёта и акта сверки — e-mail контрагента из 1С (если их несколько — выбор в окне подтверждения); для доверенности — из списка своих.
- Результат — «ждёт подтверждения»; в окне — **сам PDF**, кому, тема, текст → «Отправить» / «Отмена». Вложение — только PDF агента, один адресат + скрытая копия.
- Журнал: кому, что, когда, кто подтвердил.

### Приёмка C

- Тестовый ящик Славы (пароль приложения вводит Слава в окне): «Проверить» → письмо себе; счёт контрагенту с тестовым адресом Славы → подтверждение → письмо + скрытая копия.
- Попытка модели отправить на свой адрес — инструмент не принимает адрес (тест); превышение лимита — отказ с текстом; рубильник — отказ.

## Часть D — «Данные на …» в каждом ответе (решение Славы 18.10)

**Почему:** учёт в 1С отстаёт от жизни — выписки загружают раз в несколько дней, месяц доводят к концу. Покажем «должника», который уже заплатил, — директор больше не откроет. Лучше честно назвать дату.

- **Каждый инструмент с цифрами** (деньги, должники, кредиторы, продажи, налоги) возвращает блок `as_of`: дата последней **проведённой банковской выписки** по каждому счёту организации (поступления и списания), дата последнего проведённого документа в базе, последний закрытый месяц (если есть «Закрытие месяца»).
- **Модель обязана назвать дату** в ответе: «Данные 1С на 15.10 (выписка Kaspi — 15.10, Halyk — 12.10)». Требование — в описании инструментов и в поле `instructions` MCP-сервера.
- **Давность:** выписка по счёту старше 3 рабочих дней (настраивается на вкладке «MCP») → предупреждение «выписки по Halyk не загружены с 12.10, остаток и должники могут быть неточны».
- **Только 1С:** не пишем «по данным банка», не досчитываем.
- Реализация — один общий помощник «свежесть» (OData, кэш на минуту) на все инструменты; первым — `cash_balance`. `print_invoice` не касается — счёт на свою дату.
- В облаке (WhatsApp/Telegram, утренняя сводка) строка «данные на …» есть всегда.

**Приёмка D:** в v19/v20 `cash_balance` → в ответе Claude дата по каждому счёту; в копии базы удалить последние выписки по одному счёту → предупреждение о давности по нему.

## Правила

На копиях эталона; настоящих клиентов и чужих адресов — никаких; письма — только на тестовые адреса Славы. Пароли почты — только в окне агента, не в чат и не в журнал. Каждая часть — снимки и «готово к приёмке».
