## Часть C — вкладка «SMTP» и отправка документов (СЕЙЧАС)

<Warning>
  **Исправление Славы 18.10 (вечер): окно подтверждения отправки — УБРАТЬ.** Никто не ходит на сервер нажимать «Отправить». `send_document` отправляет **сразу**. Перед отправкой ИИ может предложить показать документ в чате (это уже умеет `print_*` — PDF и превью в ответе MCP); решает пользователь в чате. Одобрения (менеджер → бухгалтер) — позже, только в облаке. Окно «Отправить по почте», уведомление в трее о письме и `send_status` — удалить.
</Warning>

**Цель приёмки:** Слава сам вводит пароль приложения в окне агента → просит Claude «отправь счёт №4 из v19 на мой тестовый адрес» → письмо с PDF приходит, копия — себе, запись — в журнале.

### Вкладка «SMTP» (на каждую базу)

Название вкладки — **SMTP** (инженерное, только отправка; приём почты не делаем). Место — **после «Печатные формы», перед «Журнал»**.

- Сервер, порт, SSL/TLS, логин, **пароль приложения** — вводится только в окне, хранится зашифрованным для этой машины (DPAPI), в окне — точки, в журнал и логи не попадает. Имя отправителя.
- Подсказки для Gmail / Mail.ru / Yandex / Outlook (сервер, порт, где взять пароль приложения).
- **«Проверить»** — тестовое письмо на адрес отправителя.
- **Свои адреса** — список (главбух, директор, тестовый адрес Славы). На них можно отправлять любой документ агента; доверенности — **только** на них.
- Подсказка под списком — **дословно**: «Доверенности уходят только на эти адреса (руководитель, бухгалтер). Счета и акты сверки — на любой e-mail: адрес назовёт ИИ, иначе — e-mail контрагента из 1С.» (Убрать «дальше человек перешлёт сам» и «каждое письмо вы подтверждаете в окне агента».)
- **Скрытая копия себе** — вкл. по умолчанию (адрес отправителя).
- **Лимиты** — 10 писем в час, 50 в день (настраиваемо).
- Шаблон темы и текста письма (РУ/КЗ), подпись.
- **«Почта выключена»** — рубильник (и в меню трея).
- Облако (серый блок): подтверждение с телефона, права по людям, цепочки одобрений.

### Инструмент `send_document`

- Параметры: `base`, документ (`invoice` + номер / `last`; дальше — доверенность, акт сверки), адресат, необязательная приписка (до 300 символов).
- **Адресат (исправление Славы 18.10):**
  - **Счёт на оплату и акт сверки — на любой e-mail.** Адрес передаёт модель (пользователь назвал в чате); если не передан — e-mail контрагента из 1С (если их несколько — инструмент возвращает список, ИИ спрашивает пользователя в чате). В этих документах нет ничего секретного; ответственность за адресата — на том, кто попросил. Проверки адреса нет — журнал, скрытая копия, лимиты.
  - **Доверенность — только на «Свои адреса»** (руководитель, бухгалтер). Другой адрес — отказ с текстом «Доверенность отправляется только на адреса из списка «Свои адреса» во вкладке SMTP». Дальше человек пересылает сам.
  - Текст отказов и подсказок — дословно с названиями полей во вкладке («Свои адреса», не «доверенные адреса»).
- **Отправляет сразу** и возвращает итог: «отправлено на …, копия на …» или ошибку SMTP с текстом. Вложение — только PDF, сделанный агентом; один адресат + скрытая копия. Тема и текст — из шаблона вкладки SMTP + приписка от модели.
- В описании инструмента (и в `instructions` сервера): «Перед отправкой предложи пользователю показать документ — вызови print\_\* и покажи PDF; отправляй, когда пользователь согласен или явно просит отправить сразу».
- **`tools/list_changed`:** сервер объявляет `capabilities.tools.listChanged: true` и шлёт уведомление `notifications/tools/list_changed` всем открытым сессиям, когда набор инструментов меняется (обновление агента, включение/выключение почты рубильником, запись на «Доступе»). Клиенты, которые это поддерживают, подхватят новые инструменты без перезапуска; остальным — новая сессия. Касается всех инструментов, не только почты.
- **Журнал:** «Счёт №4 от 13.04.2022 (v19) отправлен на a\*\*\*@example.com, запросил claude-code 2.1 (127.0.0.1), 18.10 15:42» — без содержимого письма.

### Приёмка C

1. Слава вводит SMTP и пароль приложения во вкладке → «Проверить» → письмо себе.
2. В Claude: «отправь счёт №4 из v19 на [vova@skp.kz](mailto:vova@skp.kz)» → Claude предлагает показать счёт → «да» → PDF в чате → «отправляй» → письмо пришло, PDF открывается, копия у отправителя, строка в журнале. Никаких окон на стенде.
3. Счёт на адрес, которого нет ни в 1С, ни в своих — уходит, строка в журнале с адресом. Доверенность на такой адрес — отказ (тест). Превышение лимита — отказ. Рубильник — отказ.
4. Пароль не виден нигде: ни в конфиге открытым текстом, ни в журнале, ни в ответе MCP (тест).

## Часть D — «Данные на …» в каждом ответе (ПОСЛЕ C)

**Почему:** учёт в 1С отстаёт от жизни — выписки разносят раз в несколько дней, месяц доводят к концу. Покажем «должника», который уже заплатил, — директор больше не откроет. Лучше честно назвать дату.

- **Каждый инструмент с цифрами** (деньги, должники, кредиторы, продажи, налоги) возвращает блок `as_of`: дата последней **проведённой банковской выписки** по каждому счёту организации, дата последнего проведённого документа в базе, последний закрытый месяц (если есть «Закрытие месяца»).
- **Модель обязана назвать дату**: «Данные 1С на 15.10 (выписка Kaspi — 15.10, Halyk — 12.10)». Требование — в описании инструментов и в поле `instructions` MCP-сервера.
- **Давность:** выписка по счёту старше 3 рабочих дней (настраивается на вкладке «MCP») → «выписки по Halyk не загружены с 12.10, остаток и должники могут быть неточны».
- **Только 1С:** не пишем «по данным банка», не досчитываем.
- Один общий помощник «свежесть» (OData, кэш на минуту) на все инструменты; первым — `cash_balance`. `print_invoice` не касается.

**Приёмка D:** `cash_balance` → в ответе Claude дата по каждому счёту; в копии базы удалить последние выписки по одному счёту → предупреждение о давности.

### `print_power_of_attorney` — доверенность (форма Д-1, приказ МФ РК № 562)

- Параметры: `base`, `number` или `last`, поиск — `employee` / `period`.
- Шапка: организация, БИН, адрес, банковский счёт (основной) — из 1С. Номер, дата выдачи, «действительна по», кому выдана (ФИО, должность), **удостоверение личности (номер, дата, кем выдано) — из 1С**, от кого получить, по какому документу, перечень (наименование, ед., количество прописью).
- Удостоверение: в состав OData добавляется регистр документов физических лиц (при онбординге и «Применить»). **Отдельного инструмента для чтения документов физлиц нет** — данные используются только внутри печати доверенности, наружу MCP их не отдаёт (только в PDF).
- Подписи: «Руководитель организации … /\<от имени>/», «Главный бухгалтер … /\<из настроек или пусто>/», печать поверх строки руководителя — как в счёте.
- Отправка `send_document` — **только «Свои адреса»** ([0014](/decisions/0014-pochta-predohraniteli)).
- Файл: `Документы\Bilem\<база>\Доверенности\Доверенность №… от … — <ФИО> (<база>).pdf`.

### `print_reconciliation` — акт сверки взаимных расчётов

- Параметры: `base`, `counterparty` (БИН или название), `period_from`, `period_to`, `contract` (необязательно; без него — все договоры контрагента, разбивка по договорам).
- Левая половина — наши данные из 1С: сальдо на начало, документы (реализация, оплата и т. д.) по дебету/кредиту, обороты, сальдо на конец; итог прописью «задолженность в пользу …». Правая половина — **пустая** (контрагент заполняет сам) или зеркальная, если включена галочка.
- Подписант контрагента — «/\_\_\_\_\_\_\_\_\_\_\_\_/» (мы его не знаем); наша подпись и печать — как в счёте.
- Отправка — на любой адрес (как счёт). Файл: `…\Акты сверки\Акт сверки — <контрагент> — <период> (<база>).pdf`.
- Блок `as_of` (часть D) — в ответе обязательно: акт строится по проведённым документам на дату.

### Журнал аудита (для всех печатных и почтовых инструментов)

Одна строка на событие — в «Журнале» и в файле `C:\ProgramData\Bilem\logs\audit-ГГГГ-ММ.jsonl` (только дописывание; доступ — Администраторы и SYSTEM):

- время; база; действие (`print` / `send` / `send_failed`); вид и номер документа; путь к PDF и его SHA-256;
- **кто запросил:** программа из MCP `initialize` (`clientInfo.name` и версия, напр. «claude-code 2.1»), адрес источника (127.0.0.1 или адрес в сети), пользователь сети Tailscale, если запрос пришёл через `tailscale serve` (заголовки `Tailscale-User-Login` / `Tailscale-User-Name`); позже в облаке — канал и номер (WhatsApp/Telegram);
- для отправки — адрес получателя, адрес скрытой копии, результат SMTP.
- **Без содержимого:** ни ИИН, ни удостоверения, ни сумм по строкам в журнал не пишем — только ссылка на файл и хеш.

### Приёмка E

1. Доверенность из 1С (v19) → PDF совпадает по полям с образцом Славы, удостоверение подставлено, печать/подпись на месте; отправка на чужой адрес — отказ, на «Свои адреса» — уходит.
2. Акт сверки по контрагенту за квартал → сальдо и обороты сходятся с отчётом 1С «Акт сверки» за тот же период; правая половина пустая, с галочкой — зеркальная.
3. Журнал: строки print/send с программой, источником, хешем; через Tailscale — с пользователем сети. В журнале нет ИИН и номера удостоверения (тест).

## Часть B — черновики и подтверждение записи в 1С (НЕ БРАТЬ, ждёт утверждения)

**Сценарий:** «вот реквизиты — заведи контрагента, выставь счёт на 50 000 и отправь» → человек нажимает «Подтвердить» (создать в 1С) и «Отправить» (часть C).

- Инструменты записи ничего не пишут в 1С сами: черновик в агенте → окно подтверждения → в 1С пишет только кнопка «Подтвердить» (мимо модели). Только белый список ([0013](/decisions/0013-belyj-spisok-zapisi)) и только где запись включена на «Доступе». Документы — непроведённые.
- Инструменты: `find_counterparty` (+ проверка контрольной суммы БИН/ИИН), `draft_counterparty` (дубль по БИН не создаётся), `draft_invoice`, `copy_invoice` («как в прошлом месяце»), `draft_status`.
- **Пересмотреть до утверждения:** окно подтверждения на сервере Слава отменил для почты (18.10) — для записи в 1С механизм подтверждения решаем отдельно (вероятно, «показать черновик в чате → пользователь говорит «да»»).

### F2. Версии и MSI

- SemVer, тег `vX.Y.Z` (бета — `vX.Y.Z-beta.N`). Одна версия везде: сборки, файлы (`ProductName` = «Bilem Agent», `ProductVersion`), MSI.
- MSI (WiX): установка на машину, `MajorUpgrade`, разрешить откат на предыдущую версию. Данные в `C:\ProgramData\Bilem` (базы, токен MCP, печати, SMTP, журнал) при обновлении **не трогаются**; при удалении — остаются, если не отмечено «удалить настройки».
- Ярлык, автозапуск в трее, служба (если есть) — как сейчас.

### F3. Сборка и релиз (GitHub Actions в `bilem.ai`)

- По тегу: windows-latest → тесты → MSI → `SHA256SUMS` → **подпись релиза Ed25519** (файл `SHA256SUMS.sig`; закрытый ключ — секрет `RELEASE_SIGNING_KEY`, открытый — зашит в агент) → GitHub Release (`-beta` → prerelease) с заметками из `CHANGELOG.md`.
- Ключ Ed25519: генерирует Земля на стенде, секрет кладёт Слава (или `gh secret set` с его одобрения), локальную копию удалить, резервную копию — Славе в менеджер паролей. В чат и журнал — никогда.
- **Шаг Authenticode-подписи — заготовкой:** официальное действие Microsoft Artifact Signing (OIDC: `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_SUBSCRIPTION_ID`, endpoint, account, certificate profile — переменные репо). Пока переменных нет — шаг пропускается, сборка не падает. Подписывать: exe агента, службы, помощники com32/com64, MSI. Решение — [0012](/decisions/0012-podpis-koda).

### F4. Обновления в агенте (вкладка «Сервис» → «Обновления», сейчас серая — оживить)

- Текущая версия; канал: **«Получать бета-версии»** (галочка); «Проверить сейчас»; автопроверка раз в сутки (GitHub API `releases/latest` / список релизов, без токена, с `User-Agent` и ETag; сеть недоступна — тихо, строка в журнале).
- Есть новее → «Доступна 0.3.1» + заметки → **«Обновить»**: скачать MSI и `SHA256SUMS(.sig)` в `ProgramData\Bilem\updates`, проверить подпись Ed25519 и хеш; если MSI подписан Authenticode — проверить издателя «SKP.kz LLC». Не сошлось — отказ, MSI удалить, строка в журнале.
- Установка: `msiexec /i … /qn /norestart /l*v <лог>` через отдельный помощник (агент закрывается, помощник ставит и запускает агент снова). После запуска — строка «Обновлено с X на Y» в журнале и в аудите.
- Предыдущий MSI хранится → **«Откатить на X»**.
- Без интерактива в режиме службы: только проверка и уведомление; ставит человек кнопкой.

### F6. Находки приёмки на боевом сервере (18.10)

1. **Нет .NET Framework 4.8.** MSI установился, но `bilem-agent.exe` при запуске падает с системным окном «This application requires .NETFramework,Version=v4.8», за ним — пустое чёрное окно «Bilem Agent». На серверах бухгалтерии часто Windows Server 2012 R2 / 2016 / 2019 (из коробки — 4.5.2 / 4.6.2 / 4.7.2).

   **Решение Славы 18.10 (ночь) — делать сейчас, пересобрать бету. Только MSI, никаких exe-установщиков** (MSI — запись в «Программах», удаление, обновление кнопкой; exe не выкладываем).
   - **Порядок — главное (уточнение Славы):** вопрос про .NET — **первым экраном**, сразу после запуска MSI, **до копирования файлов и до любых системных окон**. Неправильно (как в beta.1): поставить → программа падает с системной ошибкой → Windows сама предлагает .NET. Правильно: запуск MSI → «нет .NET 4.8, без него не запустится — установить?» → дальше установка. Если получится поставить .NET **до** Bilem Agent (из UI-последовательности, до InstallExecute) — так и делай; нельзя — сначала агент, сразу за ним .NET, но вопрос всё равно первым.
   - **MSI сам проверяет .NET 4.8** при установке: `HKLM\SOFTWARE\Microsoft\NET Framework Setup\NDP\v4\Full\Release` ≥ 528040.
   - Нет 4.8 → окно в мастере установки (RU, EN — по языку системы): **«На этом компьютере не установлен .NET Framework 4.8. Без него Bilem Agent не будет работать. Установить сейчас? Скачается с сайта Microsoft (~70 МБ), может понадобиться перезагрузка.»** → «Установить» / «Отмена» (отмена — установка не начинается).
   - «Установить» → MSI ставит Bilem Agent и **сразу после завершения** запускает официальный web-установщик Microsoft .NET 4.8 (`ndp48-web.exe`, ~1,4 МБ, подписан Microsoft — кладём внутрь MSI; запуск — custom action после InstallFinalize, потому что внутри транзакции одного установщика другой запускать нельзя). Ярлык «Запустить Bilem Agent» в конце мастера — только если .NET уже есть; иначе текст «После установки .NET (и перезагрузки, если попросит) запустите Bilem Agent с ярлыка».
   - Нет интернета → вместо запуска — ссылка на офлайн-установщик (dotnet.microsoft.com/download/dotnet-framework/net48).
   - Тихая установка (`/qn`, обновление кнопкой) — без окон: там .NET уже есть; если вдруг нет — отказ с понятной строкой в логе.
   - **Пустое чёрное окно**: ни при каком сбое запуска не показывать пустую рамку — либо окно агента, либо понятная ошибка.
   - README, заметки к релизу — строка «Требования: Windows 10 / Server 2012 R2+, .NET Framework 4.8 (установщик предложит поставить)». docs.bilem.ai/install правлю я (Cowork).
   - **Тест**: копия/ВМ без 4.8 → MSI предлагает .NET → «Установить» → агент установлен, .NET поставился, перезагрузка (если нужна) → агент запускается → мастер онбординга. «Отмена» → ничего не установлено.
   - **Выпуск**: `v0.3.0-beta.2` (с гонкой токенов). Тег beta.1 не перевыпускать. Проверку обновления кнопкой сделаем на beta.2 → beta.3.

### F5. Приёмка (Слава, боевой сервер, одна база)

1. Земля выпускает `v0.3.0-beta.1` → Слава скачивает MSI с GitHub Releases на сервер → установка → онбординг с одной базой → MCP с Мака через Tailscale. Всё, что споткнулось, — в журнал v0.3.
2. Земля чинит (или делает заметную мелочь, напр. строку на «О программе») → `v0.3.0-beta.2`.
3. На сервере: «Проверить» → «Обновить» → агент перезапустился, база, настройки, токен MCP, печати, SMTP на месте; строка в журнале; «Откатить» → вернулась beta.1 → снова «Обновить».
4. Подменённый MSI (испорченный байт) — отказ, ничего не установлено (тест).

## Часть G — «Кто нам должен» и «кому должны мы» (В ОЧЕРЕДИ, 18.10)

<Note>
  **В очереди доработок, не брать до команды Славы.** Порядок: сначала приёмка beta.1 на боевом сервере и обновление на beta.2 (F5), потом — G. Обещано в посте для бета-тестеров, поэтому G — первая в очереди после F.
</Note>

**Цель приёмки:** «кто нам должен больше 30 дней?» → список контрагентов с суммой, датой самого старого долга и днями; итог; «данные 1С на …».

### `receivables` — дебиторка (кто должен нам)

- Источник — регистр бухгалтерии (как акт сверки): сальдо по счетам расчётов с покупателями (1210 с субсчетами; авансы полученные 3510 — зачётом по тому же контрагенту и договору, показать отдельной колонкой) на дату, субконто — контрагент, договор.
- **Возраст долга:** по документам расчётов, если аналитика ведётся; иначе — FIFO: долг закрывается оплатами от самых старых реализаций, остаток датируется непогашенными реализациями. Метод — в ответе (`aging_method`).
- Параметры: `base`, `organization`, `as_of_date` (по умолчанию сегодня), `min_days` (0/30/60/90), `min_amount`, `counterparty`, `top` (по умолчанию 20, сортировка по сумме).
- Ответ: строки (контрагент, БИН, договор, сумма, аванс, самый старый неоплаченный документ, дней), корзины 0–30 / 31–60 / 61–90 / 90+, итог, блок `as_of` (часть D) — **обязателен**; предупреждение о давности выписок стоит первым («должник мог уже заплатить»).
- Только чтение. Без ИИН физлиц-контрагентов в ответе (как везде).

### `payables` — кредиторка (кому должны мы)

Зеркально: 3310 с субсчетами, авансы выданные 1710; возраст — по поступлениям.

### Связка с печатью и почтой

В описании инструмента: «по должнику можно сразу сделать акт сверки (`print_reconciliation`) и отправить ему (`send_document`)». Отдельной рассылки должникам нет.

### Приёмка G

1. На v19: итог `receivables` сходится с ОСВ по 1210 (и сальдо по 3510) на ту же дату до тиына.
2. Возраст: 2–3 контрагента сверить руками по карточке счёта.
3. `min_days=30` отсекает свежие долги; `as_of` с предупреждением о давности есть в ответе.
4. docs.bilem.ai → «Инструменты»: строку «Кто нам должен…» перенести из «Скоро» в «Уже работает» (сделаю я, Cowork, после приёмки).
